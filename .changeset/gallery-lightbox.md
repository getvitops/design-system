A gallery/lightbox that is a fully working modal lightbox with **zero JavaScript**, plus
`ImageMetadata` support in `<Carousel />`.

Only `@getvitops/core`, `generator` and `astro` change here. This changeset makes **no
consumer-facing change** to `utils`, `cli` or `vite` — they still ship in this release because
the six share one version, but from a different changeset (`localbusiness-schema.md`) that
touches `utils` and `generator` for an unrelated reason.

**Breaking — `css`/`bricks`/`tailwind` (all formats):** the `.lightbox` thumbnail grid is now
`.gallery`, so it composes with the dialog it opens (`.lightbox-dialog`, unchanged) rather than
sharing its name. `vitops lint --fix` cannot cover this: `movedTokens()` renames colour token
names only, and there is no class-rename mechanism in `@getvitops/cli`. Migrate by hand:

| Old                | New               |
| ------------------ | ----------------- |
| `.lightbox`        | `.gallery`        |
| `.lightbox__item`  | `.gallery__item`  |
| `.lightbox__thumb` | `.gallery__thumb` |

`.lightbox-dialog` and its `__content` / `__image` / `__close` / `__nav` / `__nav-button` /
`__caption` parts are unchanged.

**Added — `css`/`bricks`/`tailwind` (all formats):** `patterns/gallery.css` — the `.gallery` grid,
now on the token cascade (`--br-gallery` etc.) it only half-had before.

**Added — `wc`:** `<wc-gallery>` (`@getvitops/core/elements`). Wraps a `.gallery` grid of
`command="show-modal"` triggers and the `.lightbox-dialog`s they open. With no JS, each trigger is
a real Invoker Commands button for its own dialog — open and close both work. `<wc-gallery>` adds
what the fallback deliberately cannot contain: prev/next, arrow keys, swipe (horizontal to step,
vertical to dismiss), an announced image counter, neighbour preload, and a thumbnail → full-image
`document.startViewTransition` morph where supported. Prev/next can't exist in the fallback — a
second `show-modal` invoker inside an already-open dialog stacks a second modal rather than
replacing the first — so it is generated by the element, never authored, the same rule
`<wc-tree>`'s search field follows.

**Added — `astro`:** `<Gallery />` (`@getvitops/astro/components/Gallery.astro`) — emits a
`.gallery` grid plus one `.lightbox-dialog` per image and its own `<wc-gallery>`; do not wrap it in
one. Images take `string | ImageMetadata`, rendered through a new internal `<ResponsiveImage />`
helper: a plain string renders the same raw `<img>` every component here used before, unchanged;
an `astro:assets` import renders through `<Picture />` for AVIF/WebP derivatives.

**Changed — `astro`:** `<Carousel />`'s `CarouselSlide.src` now also accepts `ImageMetadata`,
through the same `<ResponsiveImage />` helper, plus a new `formats` prop. Every existing
string-`src` call site renders byte-identical markup — purely additive.

**Added — `wc`:** the Invoker Commands API (`<button command commandfor>`) polyfill
(`invokers-polyfill`, feature-detected via `@getvitops/core/polyfills`) — resolves the TODO
`polyfills.ts` carried since 4.0. `<wc-gallery>`'s fallback and `<Drawer />` (which already emitted
`command="show-modal"` unconditionally) both now get real cross-browser coverage rather than
depending on it being "too new to rely on yet." Fetched only in an engine that doesn't support the
API natively, so a current browser downloads none of it.

**Migration:** rename `.lightbox` → `.gallery` and `.lightbox__item`/`.lightbox__thumb` →
`.gallery__item`/`.gallery__thumb` wherever authored (see table above); everything else is
additive. Consumers using the CSS pattern with no JS need no other change — the fallback markup is
unchanged in shape, only the class names moved.
