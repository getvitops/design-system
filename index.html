Vitops · CSS framework

Every class, with a live demo.

Named width tracks, container-gated utilities, relationship-based rhythm, schema-driven colour and type, a staged animation library, and a component layer — each documented below with a working example rendered by the real framework CSS. The table of contents is itself built from framework classes (.toc-layout / .drawer / .scroll-target-group).

00Conventions

Names follow Tailwind’s vocabulary wherever there’s an equivalent (items-*, justify-*, text-*, bg-*, the sm/md/lg/xl breakpoints), so one vocabulary spans the CSS, Bricks, and Tailwind outputs. The only difference is the variant separator: Tailwind uses : (and @ for container queries); the CSS/Bricks formats swap it for a dash -. So Tailwind’s @md:split-1-2 and hover:flip-fade-in become md-split-1-2 and hover-fade-in here.

Three markers appear on headings and individual classes:

responsive Has container-query variants gated by a bare breakpoint prefix, resolved against the nearest container (not the viewport): sm- 30rem · md- 48rem · lg- 64rem · xl- 80rem. e.g. flex-col md-flex-row.

state Reacts to an interaction or activation state. For animation effects, trigger-prefixed variants exist — hover-, focus-, active- (pair with .transition for a reversible flip). For components it means :hover / :focus-visible / .is-active / [open] states.

Tailwind Not emitted in the tailwind build. Tailwind already provides the equivalent — either a native utility (flex, items-*, hidden, sr-only) or one generated from a @theme token (bg-*/text-*/border-* colours, drop-shadow-*, the m-* spacing scale). In that format, use Tailwind’s own class; these exist only in the css/bricks outputs.

Note: the tailwind build is a minimal token + utility + engine + structure layer. The component library (dialogs, drawers, carousel, forms, …) and extended structural utilities (cluster, subgrid, sticky, …) ship only in the css/bricks outputs — they’re not Tailwind-tagged (Tailwind has no equivalent), they’re simply outside that bundle.

02Color & shadow

Every colour token is named --color-<target>-<role>[-<variant>], where target is one of bg text icon border. The target sits inside the name deliberately: bg-danger-muted and text-danger-muted are different tokens, so nothing has to arbitrate between them. The token name is also the class name — write class="bg-danger-muted" and you are using --color-bg-danger-muted. Underneath, each hue is an 11-step OKLCH scale on a shared lightness ladder, so a step means the same lightness in every hue.

Variants are ordinal: xx-muted < x-muted < muted < (bare) < bold < x-bold. bold means more emphatic in the current appearance, not darker — the appearance decides polarity.

Surface roles (neutral, surface) are page and panel colours: bg-<role> is the card, bg-<role>-muted the page behind it, bg-<role>-x-muted a well. Full text scale, plus border-<role>-bold as the contrast-guaranteed boundary and glass / --overlay on surface.

Chromatic roles (ui-primary ui-secondary ui-accent brand-primary brand-secondary info success warning danger) are signal colours. Backgrounds are either tints (bg-<role>-x-muted / -muted) or solids (bg-<role>-solid / -solid-bold / -solid-x-bold) — there is deliberately no bare bg-<role>, because "how loud?" is a question you should answer. text-on-<role> is the guaranteed foreground for the solid family.

Seeded hues: pine navy amber rust cobalt grey — numeric steps 50…950 (e.g. bg-pine-100), fixed at build and not re-pointed in dark mode. Contrast is enforced at build time and fails the build: text ≥ Lc 75 on its primary background, ≥ Lc 60 on secondary planes, icons and the surface boundary ≥ Lc 45, in both appearances.

.text-{role}[-bold|-muted|-x-muted|-xx-muted] / .text-on-{role}Tailwind

.icon-{role}[-muted] · .border-{role}[-muted|-bold] · .glassTailwind

.{bg|text|icon|border}-{hue}-{50…950}Tailwind
Raw scale (fine control, bypasses theming). e.g. .bg-pine-100, .text-grey-800. These are fixed — unlike role tokens they are not re-pointed in dark mode.

04Structural patterns

Prefer .subgrid over auto-flow grid / masonry. In almost every layout, subgrid is the correct default: it aligns rows and columns across siblings in a controlled, predictable grid. Auto-flow placement (and .masonry) let items break wherever they fit — you rarely actually want those arbitrary breaks. Reach for auto-flow / masonry only when ragged, packed placement is genuinely the goal (e.g. a photo wall); otherwise start from .subgrid.

05UI patterns

Component patterns generated from design-system.json. Actions come in two tiers, named for intent rather than prominence: .cta is persuasion — it draws attention to drive an action; bare <button> / .btn is affordance — it says only "this is interactive". Both are classes, so either works on any element: a CTA is usually an <a>, because it navigates.

Buttons and links pair an element with a class in one zero-specificity rule (:where(button, .btn) / :where(a, .link)) — no class needed for the base, and any explicit class overrides it.
