Vitops · CSS framework

A small layout vocabulary you can hold in your head.

Named width tracks, container-gated utilities, relationship-based rhythm, and a staged animation library — built for the Bricks page builder. Every demo below runs on the real framework CSS.

Why this exists

Applying a few well-named classes is far easier to manage and keep consistent than configuring the same settings by hand on every element in the Bricks UI — change the class once, every element follows. And Bricks ships no animation library, so this provides one.

Composing within a track

Tracks set how wide a block is; a handful of utilities set what happens inside it. All are container-gated with the same sm/md/lg/xl suffixes, so they reshape as the container grows — mobile-first, stacked by default.

.flex · .flex-row · .flex-col

Turn a block into a flex container and set its direction. .flex-row-md stays stacked until the container hits md, then goes side-by-side.

.split-1-2 · 2-1 · 1-3 · 3-1

Proportional columns inside a flex parent — a 1∶2 sidebar, a 1∶3 media tile. Bare .split gives equal columns.

.align-* · .justify-*

Cross-axis (start / center / end / stretch) and main-axis (start / center / end / between) control for flex parents.

.text-start · .text-center · .text-end

Logical text alignment, also tier-gated (.text-center-md) for per-breakpoint shifts.

The whole layout vocabulary is roughly two dozen names: four tracks, a flex toggle, four splits, alignment, and text — composable, and small enough to diagram.

02Color

Six raw ramps, seven steps each (dark → light). Semantic roles map onto them, so re-aiming a role — success from pine to cobalt — is a one-line change.

Semantic roles

02bDark mode

Named ramps never change — pine is always pine. Dark mode only remaps which step each semantic role points at, so components referencing semantic tokens (--color-surface, --color-success) adapt automatically. Bricks toggles the mode; the build emits the remapping.

Try it — this toggles [data-theme="dark"] on the page, exactly what the generated dark block keys off:

--color-surfacesurface role
--color-success-dsuccess role
--color-brand-primary-dbrand (identity)

Watch surface and success flip in dark (they invert), while brand-primary holds steady — it has no dark remap, so it resolves the same in both modes.

Authoring dark in colors.json

Three forms, increasing in control. The build resolves each step's dark value in priority order: explicit override → invert mirror → identity.

String — no dark remap

"info": "cobalt"
Light maps 1:1 to the ramp; dark stays the same. For roles that look right in both modes.

Invert — symmetric flip

"surface": { "name": "navy", "invert": true }
Dark mirrors every step: xxd↔xxl, d↔l, base→base. The common dark-mode case.

Invert + overrides

"success": { "name": "pine", "invert": true, "dark": { "base": "l" } }
Invert sets the baseline; explicit per-step overrides win where the mechanical flip isn\'t right.

In the Bricks palette each semantic colour carries both a light and dark reference to its named variable, so the indirection holds in both modes and Bricks\' own light/dark toggle drives it.

02cComponent patterns

A few interaction patterns encode the hover/active/focus behaviour once, so applying them is consistent and judgment-free. Buttons and links are styled at the element level (via zero-specificity :where(), so any class — including Bricks\' own — overrides them); badges and cards are classes.
